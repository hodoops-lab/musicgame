# 드럼 마스터 (Drum Master) — 프로젝트 인계 문서

중학교 음악 수업(리듬 첫 시간)용 웹 게임입니다. **빌드 과정이 필요 없는 단일 HTML 파일**이며,
CSS/JS/이미지(base64)가 모두 그 안에 들어있습니다. 브라우저로 열기만 하면 바로 실행됩니다.

- 메인 파일: `드럼마스터_악보매칭_리듬게임.html` (원하면 `index.html`로 이름을 바꿔도 무방)
- 외부 의존성: Google Fonts CDN 링크 2개뿐 (Jua, Noto Sans KR, IBM Plex Mono). 그 외 전부 인라인.
- 서버/빌드 불필요 — 더블클릭해서 브라우저로 열면 끝.

## 앱 구조 (화면 흐름)

```
메인 메뉴
├── 1) 악보 매칭 게임
│   ├── 학습 화면 (실제 드럼 패드 사진 + 파트별 오선 위치 범례)
│   ├── 1. 오선보 읽기 (오선 기호 → 4지선다, 무한 출제 + 오답 간헐적 재출제 + 끝내기 버튼)
│   └── 2. 드럼 패드 위치 찾기 (오선 기호 → 실제 패드 사진에서 클릭해서 찾기)
└── 2) 리듬 게임
    ├── 카테고리 선택 (8비트 / 16비트 / 8+16비트 혼합)
    ├── 단계 선택 (1~10단계, 단계별 30초)
    └── 플레이 화면 (오선보 위로 음표가 흘러오고 스페이스/클릭/터치로 타이밍 맞추기)
```

## 핵심 설계 결정 (왜 이렇게 되어 있는지)

### 드럼 파트 & 오선 위치
사용자가 업로드한 실제 전자드럼 패드 사진(Hos:m 롤업 드럼) 기준 8개 파트:
스네어, 킥(베이스드럼), 탐1/탐2/탐3, 하이햇, 크래시, 라이드.

`STAFF_LINES_Y` 배열(5줄) 기준으로 각 파트의 오선 위치가 정의되어 있습니다 (`PARTS` 객체, 스크립트 상단 근처).
- 킥: 맨 아래 칸 / 탐1: 맨 위 칸 / 탐2: 아래서 4번째 줄 / 스네어: 아래서 3번째 칸 / 탐3: 아래서 2번째 칸
- 하이햇: 맨 위 줄 바로 위 칸 / 라이드: 맨 위 줄(5번째 줄) / 크래시: 오선 위 첫 레저선 (악센트 `>` 표시 포함)

⚠️ 이 위치들은 사용자가 여러 차례 명시적으로 지정/수정 요청한 값입니다. **임의로 "표준 표기법"이라며 되돌리지 마세요.**

### 드럼 패드 사진 (`PAD_PHOTO_SRC`)
사용자가 업로드한 실제 패드 사진을 크롭 + 색상 양자화(64색)해서 base64 PNG로 스크립트 최상단에 박아넣었습니다
(변수명 `PAD_PHOTO_SRC`). `PAD_LAYOUT_PHOTO` 객체에 사진 픽셀 좌표(460×275 기준)로 각 패드의 클릭 위치(cx, cy, r)가
정의되어 있는데, **이 좌표는 사진의 파란 링 색상을 Python(PIL+scipy)으로 픽셀 분석해서 산출한 값**입니다
(연결요소 분석 → 중심점/반지름 추출). 눈대중이 아니므로 함부로 재조정하지 말고, 어긋난다는 피드백이 오면
같은 방식(색상 마스크 + connected component)으로 재검출하는 걸 추천합니다.

패드 사진 위에 실제 명칭 글자가 인쇄되어 있어서, 퀴즈에서는 **각 파트 위치 위에 불투명한 마커(`.pad-target`)를
덮어서 글자를 가리고** 클릭하게 되어 있습니다 (정답 공개 시에만 저희가 그린 텍스트로 라벨 표시).

### 리듬 게임 로직
- 리듬 블록: `EIGHT_BLOCKS` / `SIXTEEN_BLOCKS` / `MIXED_BLOCKS` — 모든 블록의 길이 합은 정확히 1박.
- `SIXTEEN_BLOCKS`에는 코다이 리듬음절 3종(티 티리 / 티리 티 / 리티 리)이 포함되어 있음.
- `buildStagePhrases()`: 마디(4박) 단위로만 재생을 끊어서(마디 중간에서 끊기지 않음), 16비트 카테고리는
  **마디의 마지막 박을 항상 4분음표로 고정**해서 16분음표 묶음이 마디를 넘어가지 않도록 함.
- 템포는 고정 3단계: 1~3단계 60bpm / 4~7단계 70bpm / 8~10단계 75bpm (`stageBpm()` 함수).
- 게임 길이: 단계당 30초 (`GAME_LENGTH_SEC`).
- 음표는 항상 오선보의 "아래서 3번째 칸"(스네어 위치)에 고정 표시 — 리듬 게임에서는 어떤 드럼인지가 아니라
  **리듬 길이만** 보고 읽는 게 목적. 색상 = 리듬 길이(4분=빨강/8분=노랑/16분=파랑), 파트(kick/snare/tom 등)는
  내부적으로 블록 다양성을 위해서만 쓰이고 화면에는 안 보임.
- 같은 박(beat) 안의 8분/16분음표는 개별 꼬리 대신 **빔(가로선)으로 이어서** 그림 (`noteGroupGlyphSVG()`,
  `groupId`/`groupIdx`/`groupSize`로 태깅). DOM 엘리먼트는 그룹당 1개만 생성 (`DocumentFragment`로 일괄 삽입 —
  이걸 개별 `appendChild`로 바꾸면 첫 음표 체크 시 렉 걸리던 예전 버그가 재발함, 되돌리지 말 것).
- 사운드 3종 분리: 메트로놈(저음 110Hz, 매 4분음표마다 계속), 스페이스/터치 탭(고음 1800Hz),
  악보 매칭 퀴즈 정답/오답(각각 도미솔 협화음 / 미파 불협화음). 예전엔 음표 자동재생 사운드도 있었으나
  메트로놈과 겹쳐 혼란스럽다는 피드백으로 제거됨 — 다시 추가하지 말 것.

### 랭킹(순위) 산정 방식 — 정확도 기준 (2026-08-24 변경)
⚠️ 랭킹 점수는 **정확도(accuracy) 그 자체**를 카테고리 가중치로 보정한 값이다. "쌓은 점수 × 정확도" 같은
예전 방식(`saveGameScore()` 옛 버전)으로 되돌리지 말 것.
- **악보 매칭 게임(퀴즈)은 랭킹에 절대 점수를 주지 않는다.** `saveGameScore('quiz', ...)` 호출 자체를
  없앴고, `saveGameScore()`는 `gameType !== 'rhythm'`이면 즉시 return 한다.
- 리듬 게임만 랭킹에 반영되며, 카테고리별 가중치가 다르다: **8비트 = 정확도의 80%**,
  **16비트 / 8+16비트 혼합 = 정확도의 100%** (`saveGameScore()` 안의 `weight` 계산 참고).
- 리듬 게임의 "학습하기"(연습 모드, `rstate.practice`)는 같은 4마디를 무한 반복하는 루프라
  애초에 `finishRLevel()`(점수 저장이 일어나는 유일한 지점)까지 도달하지 않음 — 어떤 카테고리든
  학습하기는 점수를 주지 않는다. `finishRLevel()`에도 `if(!rstate.practice)` 이중 방어가 있음.
- 랭킹 점수는 판마다 (정확도 × 카테고리 가중치)를 **합산**한다 (`rhythmWAccSum` 자체가 랭킹 점수,
  `rankScore = Math.round(rhythmWAccSum)`). 처음엔 누적 평균(`rhythmWAccSum / rhythmAttempts`)으로
  했었는데, 그러면 플레이해도 점수가 안 오르는 것처럼 보인다는 실제 수업 중 피드백(2026-08-24)으로
  합산 방식으로 바꿈 — **평균으로 되돌리지 말 것.** 정확도가 높을수록 한 판에 더 많이 쌓이므로
  "그냥 많이 플레이하면 유리"해지는 옛 문제는 여전히 없음(낮은 정확도로 아무리 많이 해도 조금씩만
  쌓임). 관련 필드: `users/{uid}.rhythmRankScore`(현재 랭킹 점수 = 누적 합계), `rhythmAttempts`,
  `rhythmWAccSum`, `rankScoreV2`(마이그레이션 완료 표시). `rhythmScore`(코인 누적 점수)는 더 이상
  랭킹에 쓰이지 않고 개인 기록용으로만 남아있음.
- `saveGameScore()`의 DB 저장(`db.ref().update()`)은 이제 `.then()`/`.catch()`로 성공/실패를 확인한다 —
  성공했을 때만 `currentUser`와 점수 배지를 갱신하고, 실패하면 배지에 "⚠️ 점수 저장 실패"를 띄우고
  `console.error`로 남긴다. 예전엔 실패해도 조용히 넘어가서(화면엔 반영된 것처럼 보이지만 DB엔 저장
  안 됨) 학생별로 점수가 안 쌓이는 원인을 알기 어려웠음 — 이 에러 처리를 다시 없애지 말 것.
- 랭킹 모달(`rankingModal`)에는 리듬게임 랭킹만 표시 — 예전에 있던 "악보 퀴즈 랭킹"/"전체(총점) 랭킹"
  탭은 삭제됨. 다시 추가하지 말 것 (사용자가 명시적으로 없애달라고 요청함).
- 관리자 화면(`adminModal`)에 **"🔄 랭킹 점수 재계산" 버튼**(`migrateRankScoresToAccuracy()`)이 있음 —
  옛 방식으로 저장된 회원들의 점수를 새 방식(정확도 기준)으로 일괄 변환한다. 회원별로 저장된 리듬게임
  기록(`users/{uid}/rhythm` 그리고/또는 `leaderboards/rhythm/{uid}`)에서 정확도를 찾아 계산하며,
  `.accuracy` 필드가 없어도 `.detail` 문구(예: "16비트 4단계 (72%)")에서 `extractAccuracy()`가
  정규식으로 % 값을 뽑아내는 폴백이 있다 — **이 폴백을 지우지 말 것**. 과거 데이터에는 카테고리별
  정확도가 따로 저장되어 있지 않아서 완벽한 재구성은 불가능하다는 한계가 있음(README 작성자도 라이브
  Firebase DB에 직접 접근할 수 없어 이 버튼을 통해 관리자가 실행해야 함).
  ⚠️ 정확도를 어디서도 못 찾은 회원은 **0점으로 덮어쓰지 않고 그대로 건너뛴다** — 실제로 플레이한
  기록이 있는 회원을 잘못 0점 처리했던 버그(2026-08-24)가 있었으니, 이 "판단 불가 시 건드리지 않는다"
  원칙을 되돌리지 말 것. 건너뛰기(skip) 조건도 `rankScoreV2===true`만으로 판단하지 않고
  `rankScoreV2===true && rhythmRankScore>0`으로 검사한다 — 0점으로 잘못 마이그레이션된 회원이
  버튼을 다시 눌렀을 때 재시도되도록 하기 위함. 정상적으로(0점 아니게) 마이그레이션된 회원만
  다시 건드리지 않으므로 여러 번 눌러도 안전(idempotent).
- ⚠️ 랭킹 모달(`loadLeaderboard()`)이 점수를 읽을 때 `leaderboards/rhythm/{uid}.score`와
  `users/{uid}.rhythmRankScore` 둘 중 **더 큰 값**(사실상 "0이 아닌 실제 값" 쪽)을 쓴다
  (`Math.max(lbScore, userScore)`) — 한쪽만 무조건 우선하면, 마이그레이션 과정에서 한쪽만 갱신되고
  다른 쪽이 옛 0점 그대로 남아있는 경우(관리자 화면엔 점수가 보이는데 랭킹 화면엔 0점으로 뜨는 버그,
  2026-08-24) 재발함. 두 값이 항상 동시에 갱신되도록 코드를 고치더라도, 이 방어 로직은 유지할 것.

### 컨트롤 / 반응형
- 초록 원형 탭 버튼은 삭제 요청으로 제거됨 — 지금은 `.lane`(리듬 레인) 전체가 클릭/터치 영역.
- 스페이스바(PC) + 클릭/터치(모바일) 모두 지원. `pointer: coarse` 미디어쿼리로 터치 기기 감지해서
  `body.touch` 클래스 부여, 힌트 문구 분기(`.tap-hint.kbd` vs `.tap-hint.touchonly`).
- `@media (max-width: 680px)`에 모바일 레이아웃 조정 모여있음.

## 알려진 제약 / 다음에 이어서 할 만한 것
- 패드 사진 좌표(`PAD_LAYOUT_PHOTO`)는 특정 크롭 기준이라, 사진을 바꾸면 좌표도 다시 뽑아야 함.
- 오선보 위치는 표준 표기법이 아니라 **이 사용자의 특정 요청**을 반영한 값 — 다른 사용자/다른 교재에는
  안 맞을 수 있음. 재사용 시 확인 필요.
- 테스트는 브라우저 수동 실행 + Node.js로 JS 문법/로직만 체크(headless 렌더링 테스트는 없음).
